## 审查质量评估

### 覆盖度
- 触及了增量索引的核心函数、迁移、API、测试，发现的问题均落在“新旧语义交接”的关键路径上，覆盖面较好。
- 仍可能遗漏的重要点：
  - `wiki_dirty_pages` 失效队列写入与 `assemble_incremental` 读取之间的事务边界：是否同一事务/原子可见？跨多条语句（DELETE/UPDATE/INSERT）的原子性是否保证？
  - `generate` 长任务的取消/超时语义：`while True` 分窗循环在来源持续增长、游标前置或并发写入干扰下是否存在停滞/死循环？
  - `cursor["revisions"]` 的内存增长边界。
  - 全量核对手移动 `reconciled_at` 是否位于事务内或具备崩溃恢复语义。
  - 对象存储等多后端下 OCR/图片更新是否同样被 chunk 内容指纹覆盖。
  - 并发 job（update/generate/publish 同时存在）对同一 channel 的互斥/锁是否充分。
  - `update`→`generate`→`publish` 状态机的错误路径：生成被取消、发布校验失败兜底触发条件是否被测试覆盖。
  - `WIKI_PUBLISH_LOCK` 在新的增量流程下覆盖窗口、超时配置、死锁重试。
  - 被陈述为“无活动任务分支走 reindex 全量重建”的机制是否当前即如此，需要确认 `session["wiki_recovery"]` 恢复游标与 `session["wiki_reindex"]` 全量游标的启动条件差异；注释与实现是否一致。
  - 死信/重试队列清理（## 2.3 dead message）与增量水位、重发之间的语义；向量库回滚。
- 结论：核心路径覆盖可接受，但事务边界、任务生命周期与并发互斥的系统性校验不足。

### 准确度
- major #2、#3 依据充分（分窗枚举/走查实现与 MySQL DELETE 行乘法语义），严重程度合理。
- minor #4 影响面清楚，严重程度恰当，建议同时补一条回归测试：已应用来源进入排除任务并恢复后，其 facts 应重新纳入发布快照。
- major #1 的严重程度需要审慎：编辑消息所在 source 在此前已成功发布过（基线里已有该页面修订）时，下次编排会把编辑来源登记脏页面并修复；真正“永恒 409”只在“生成与发布从未成功需现搭基线（auto 兜底），或首次全量生成期间编辑注入脏页面后发布阶段校验失败、种子文案标记 409 即结束（无二次校验）”的窗口内成立，`assemble_incremental` 从基线合并脏页面后确实会携带旧修订。
  - 同时，`put_source` 编辑分支明确没有写 `wiki_dirty_pages`，因此页面时效保证仍依赖发布阶段其他入口（配置步骤、后续增量来源），并非当前路径自包含。
  - 因此建议将其降为“major 待确认”或要求作者论证“发布基线构造与来源编辑不会交织”，并在发布接口失败路径补充告警/护士任务。同时确认未影响 ALTER TABLE 之外的写入路径。

### 完整性
- 对 PR 意图理解到位，“全量→增量”的生命周期模型分析清晰，并抓到了“全量装配掩盖错误失效注册”这类典型增量改造问题。
- 对以下仍需确认：
  - “有活动任务时走恢复、无活动任务时走 reindex”是否当前即如此，需审阅 `store.refresh_exclusions` 中恢复与 reindex 游标启动条件差异。
  - 注释与实现同步问题，尤其增量谓词语义与恢复来源的重枚举假设。
  - 分窗循环在来源激增、游标前置、并发写入干扰下的停滞/死循环边界。

## 发现的模式

### 代码模式
- 增量三件套：内容指纹/版本号做幂等与去重；主键游标分窗做时间窗口任务；失效队列驱动局部重建。适用且值得推广。
- 依据“先删后插 vs 先查后改”区分旧全量与新局部重建语义，知识更新在事实迁移的同时只登记目标页，产生旧页修订过期/重复发布的边角问题。
- 多表 DELETE 用 `LEFT JOIN ... IS NULL` 表达“无引用”，忽略 MySQL 按行匹配带来的行乘法误删。
- 断点续跑通过 `reconcile_id` 推进水位，但恢复路径假设已被应用的来源会被重新枚举；增量谓词语义下该假设失效。
- 测试采用事务回滚隔离可行，但缺少多 job 并发/长任务取消测试。

### 架构观察
- 增量改造带来的职责转移：原全量装配被替换为基线合并增量，导致所有“生成新修订”的旧入口必须登记脏页面。
- 发布门禁（#151）与失效登记解耦，导致失去事实的旧页面不会成为脏页面、也不被重建，最终重复/过期声明进入发布。
- 游标瘦身降低了 JSON 写入放大，但装配状态（revisions）仍在内存，恢复时清理，需要验证恢复后不会丢失调用方提交。
- 清理函数 `prune` 使用 LEFT JOIN 表达无引用，忽略了快照引用保护的行乘法陷阱，且与级联删除组合放大。

## 规范完善建议

- 新增规则：
  - 增量改造必须用“失效登记强制清单”检查所有变更入口（编辑来源、撤销/隐藏、策略翻转、知识操作、OCR 更新等）是否写入脏页面；旧页面在事实迁移/删除、条目合并/拆分后必须登记。
  - 禁止用 `DELETE ... FROM s JOIN c LEFT JOIN x ... WHERE x.id IS NULL` 表达“无引用”，必须使用 `NOT EXISTS`。
  - 脏队列驱动的局部重建必须显式事务，且先删除旧修订再插入新修订，避免多版本混杂。
  - 恢复/回放路径必须枚举全部可能变更来源，且不能假设“应用标记非空”的记录会被重新枚举。
  - 发布校验失败的兜底必须显式定义日志、告警与自愈路径，不得静默 409 或依赖人工干预。
- 项目特有要点：
  - 日期时间统一 naive UTC，业务层不得自行构造；所有 SQL 写路径统一经 `mysql.py`。
  - 版本号仅在 `core/__init__.py` 与 web 前端修改，且与 CHANGELOG、镜像行为一致。
  - Go 共享契约字段演进需提供默认值并对显式列名查询保持兼容。

## 经验教训

- 增量改造的真正难点是“失效率”倍增：所有原本会被全量装配覆盖的入口，必须显式登记失效。审查增量类 PR 时要先列出所有“生成新修订”的路径，再逐一对照脏队列。
- 发布门禁单独存在并不能替代失效登记：门禁失败的自愈路径（full reindex）同时决定了增量优化的成败，必须与失效登记一起审。
- 注释与实现易发生漂移，尤其是“增量谓词”“断点续跑”“恢复”等词汇。审查时不仅要看注释，还要识别实现中会破坏语义的最小条件变化（如 `applied_key=''`），并随注释补充断言或测试。
- MySQL `DELETE` 中使用 `LEFT JOIN ... IS NULL` 需警惕行乘法；清理函数还要检查是否影响证据链。级联删除半径必须在 SQL 变更评审中单独评估。
- 测试很重要：已新增覆盖空增量/编辑/删除/级联/保留快照等场景，结论充分，不必纠结于请作者补测试。
- 后续增量改造审查时优先检查失败/恢复路径的“重新枚举假设”，以及事务边界是否覆盖增量写入。
