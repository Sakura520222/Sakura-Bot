# Sakura Wiki 使用与管理

Sakura Wiki 是 Sakura-Bot 的频道知识功能（2.3.0 引入，2.3.2 实现真正的增量索引），入口为现有 WebUI 的 `/wiki`。仓库中的 `wiki/` 是 VitePress 项目文档，两者用途不同。无需增加容器、服务、域名或站点构建工作流；知识发布只更新 MySQL。

Wiki 需要 MySQL 8.0 或更新版本（集成测试使用 8.4），首次启用时数据库账号需要创建新表的权限。

## 公开浏览

游客可以浏览已启用、公开且已发布的频道。频道数字 ID 是永久身份，标题和 Telegram username 可以改变。文章使用稳定页面 ID，管理员更换 slug 后保留旧链接。

- 首页：公开频道、最近知识更新与全站搜索。
- 频道页：主题、条目、覆盖时间与更新时间。
- 文章：每条断言的证据、有效时间、争议标记、验证日期和已发布修订记录。
- 知识地图：拖拽、缩放、平移、节点详情、邻居展开与折叠，支持类型、主题、时间、关系与关键词过滤。每次最多 120 节点、2 层邻居；键盘用户可操作旁边的节点列表。
- 时间轴：按事件时间排列，无明确事件时间时使用消息发布时间，分页在数据库中完成。
- 频道画像：真实消息条数、平均正文字符数、月度与小时分布、主题与变化趋势。主题统计可以重叠；图片 OCR 和总结不混入原消息平均长度。AI 风格分析使用明确标注的有限样本，并经过独立审校。

`accessible` 表示已经枚举当前 API 可访问的历史，不表示 Telegram 中从未删除或从未隐藏过消息。`partial` 和 `unavailable` 不应解读为“没有历史”。公开链接与原文摘录是否展示由管理员控制。

## 第一次启用

1. 使用既有方式升级主服务和前端，启动时自动创建 `wiki_*` 表。Go 助手需要与 Python 主服务一起升级，以识别新增 AI 用途。
2. 配置频道并连接 UserBot。Wiki 使用 `iter_messages(..., reverse=True, min_id=cursor, limit=100)` 持续分页；不会把“最近一周”或向量 topK 当作全量历史。
3. 进入管理侧栏 **AI 与知识库 → Sakura Wiki**，选择已核实频道。启用 Wiki，先保留人工审核模式和关闭公开访问。
4. 在侧栏「AI 配置」页面绑定「Wiki 生成」与「Wiki 审校」。审校未单独绑定时继承 Wiki 生成配置，但仍执行独立请求。其他总结、投票、助手用途不受影响。
5. 设置首次回溯范围、图片/总结来源、消息类别、语言、时区、频率和预算。输入现有 WebUI 的公开访问源地址，供 Go 助手返回可点击的 Wiki URL；未设置时助手不会猜测域名。
6. 在「任务与覆盖」启动全量回溯。旧原文归档和 SQLite 向量消息全部分页/逐文件枚举导入，只有经 Telegram 核实的原帖才能作为公开证据。总结作为独立的辅助来源保留，不假冒原帖。
7. 检查「草稿与证据」中的断言、引文和差异。审校失败、来源撤销、超预算或生成未完成时不能发布。完成后在任务页发布，再打开频道公开开关。

开启公开访问只允许已核实的公开广播频道；私有、受限和禁止转发的频道不会公开。旧配置升级后所有 Wiki 默认关闭、没有发布指针。

## 增量索引与任务恢复

2.3.2 起，日常增量任务（`update` 与定期 `reconcile`）实现真正的增量索引，Telegram 请求量、模型调用量与数据库写入量都与新增/变更消息量成正比，不再随频道历史总消息数线性增长：

- **应用水位**：每个正文 chunk 在成功写入事实与关系后记录应用标记（内容版本 + 提取结果指纹）。增量任务只枚举“当前内容版本尚有未应用 chunk”的来源——即新增消息、编辑、图片 OCR/描述变化，以及重新开放的排除记录。
- **缓存命中零写入**：提取缓存命中且来源内容与提取结果都未变化时，直接跳过事实/关系的删除重建，不再产生整轮删除加重插的写入放大。
- **轻量任务游标**：任务 `cursor` 不再保存并反复回写全量来源清单，改为按主键游标分窗枚举；任务进入终态后自动清理临时游标，只保留发布所需的修订清单。
- **页面级局部重建**：来源删除/隐藏、策略翻转与人工修订会把受影响页面登记到失效队列；增量任务只重建这些页面，未变化页面沿用既有修订，发布清单在发布时与当前快照合并。页面内容哈希未变化时不产生新修订。
- **发布去重**：发布内容指纹（页面/修订清单 + 频道画像）与当前快照一致时复用现有发布，不创建重复快照；回滚产生的快照继承源指纹。历史发布快照默认保留最近 20 个（含当前发布），可在生成设置中调整，超出的自动清理，回滚能力始终保留。
- **可再生数据清理**：无证据或快照引用的旧版本 chunk（及其提取缓存）、未被任何快照引用的失活关系边随任务清理；被发布证据引用的旧版本始终保留，以维持证据链与回滚能力。
- **核对水位**：每周历史核对在全量枚举完成的瞬间即推进水位；后续核对循环、提取或发布失败都不会把日常调度带回全量历史扫描，核对循环自身从持久游标续跑。

显式重建（首次全量回溯、重建索引、单页重建）仍会全量遍历相关来源，依靠提取缓存与应用标记快速跳过未变化部分，因此更换模型或提示词后可以安全地整体重建。新增、编辑和删除由 UserBot 事件采集；图片任务完成后复用既有 MySQL OCR/描述，图片被替换时媒体身份校验立即使旧证据不可读。

主服务 APScheduler 每 15 秒检查持久任务，按频道互斥，最多同时处理两个频道；频道内部抽取并发可配置为 1–4。租约 90 秒、每 20 秒续租，过期工作者不能继续写入修订或发布。失败按指数退避重试，FloodWait 使用 Telegram 指定的等待时间。暂停保留进度，恢复/重试从持久游标继续。Token 不可核实的请求保留预算预留，避免故障期间无限消耗。费用仅在管理员提供单价时估算。

数据库短暂不可用时，已接入频道的 Telegram 事件会暂存在 `data/wiki_events/`（可用 `WIKI_EVENT_DIR` 改目录）。恢复后先重放，再恢复频道公开访问。该目录是待送达事件，不是第二份规范知识库；必须与 `data/` 一起备份。

回放只处理已确认失败或重启遗留的事件，正常处理中的在途文件不会触发频道临时下线。真实故障积压未排干前仍暂停新任务认领：尚未写入 MySQL 的撤销事件不会改变 `source_generation`，因此不能仅凭当前数据库版本允许继续发布；这是保守的故障恢复策略。

公开权限每分钟重新核实，核实租约最多 3 分钟。服务无法确认权限时停止公开；Telegram 的外部权限变更需要被事件或下一次核实观察到，不能保证平台尚未通知时零延迟发现。管理端关闭公开、屏蔽来源、撤回页面会直接作用于数据库读取条件，没有公开内容缓存。

## 人工维护

- 锁定页面后，AI 不会覆盖它；来源撤回仍会使锁定页面不可读。
- 人工修正产生新草稿并锁定页面，复用原有可核实证据，随后通过后台任务和正常发布流程生效。
- 可更改标题/slug、归并同义名称、隐藏主题或页面。重新开放此前排除的来源后，建议运行历史核对，以重新核实内容。
- 发布在事务中写入页面/关系清单、画像和版本，再切换频道发布指针。任何一步失败均保留旧发布版本。
- 回滚重新校验当前证据；删除、屏蔽、被替换的图片和已拒绝修订不能借旧快照重新公开。
- 清除频道 Wiki 会关闭功能并删除知识、修订、任务和缓存。原消息/RAG 归档不删除；最小删除/屏蔽标记保留，防止重建复活禁止公开的来源。

主 Bot 命令：`/wiki_status 频道` 查看公开状态；管理员可用 `/wiki_build 频道` 启动回溯、`/wiki_pause 频道` 暂停。在 WebUI 中取消频道暂停并恢复任务即可继续。

## Telegram 登录

默认关闭。在 BotFather 的助手 Bot（`QA_BOT_TOKEN` 对应的 Bot）打开 Login Widget 设置，登记本站 HTTPS origin 和完整回调 `https://wiki.example.com/api/wiki/account/callback`。在 `data/.env` 设置 `WIKI_LOGIN_ENABLED=true`、`WIKI_LOGIN_ORIGIN=https://wiki.example.com` 及 `WIKI_TELEGRAM_CLIENT_SECRET`，重启服务。Client ID 取自助手 Bot 数字 ID，Secret 取自 BotFather 的登录设置。反向代理须保留公开 `Host`，回调路径的访问日志只记录路径，省略查询参数。使用 Telegram 默认的 RS256 或 ES256 签名。 [Telegram 官方配置](https://core.telegram.org/bots/telegram-login)

Wiki 在用户同意后读取 `openid profile`，保存 Telegram 数字 ID 和 OIDC subject 以绑定账户，保存昵称、可选用户名和经验证的头像快照。账户菜单可重新授权以刷新资料。公开署名默认匿名，头像与用户名默认隐藏。管理接口保持现有 WebUI 认证，管理员可通过 `/api/wiki/admin/accounts` 查询账户，并向 `/api/wiki/admin/accounts/{id}/blocked` 发送 `PUT` 和 JSON `{"blocked":true}` 撤销该用户的全部 Wiki 会话。

Wiki 启动会自动创建账户、登录流程、会话和旧 Widget 防重放表。访问 Cookie 有效期为 15 分钟，刷新凭据每次使用后轮换，单次登录最长保留 7 天。回退时先关闭 `WIKI_LOGIN_ENABLED`，保留新增表与备份。

## Go 助手

启用 Telegram 登录后，可设置 `WIKI_ASSISTANT_ENABLED=true` 并重启主服务与 Go 助手。`WIKI_ASSISTANT_PORT` 默认 `8091`，由 Go 助手监听 `127.0.0.1`，FastAPI 在同一主机或容器内转发，反向代理只需转发 `/api/wiki/assistant/`，对该路径关闭 SSE 缓冲。`WIKI_ASSISTANT_CHECKIN_ENABLED=false` 只关闭网页签到入口，助手全局签到开关也适用于网页。

网页与 Telegram 使用同一 Telegram 数字 ID、业务日时区、积分账本、免费次数和全站上限。网页对话历史使用独立会话范围。网页检索使用受公开权限与来源撤回约束的 Wiki 工具。断线后可用原请求继续接收，回放保留至下一轮、最多五分钟，并受进程内缓存容量限制。停止生成会结算退款。重启由现有账本恢复流程退回未结算预留。

`wiki_search`、`wiki_get_page`、`wiki_get_related`、`wiki_get_changes`、`wiki_get_channel_profile` 直接读 MySQL，同步检查频道权限、发布指针、来源哈希和撤销状态。没有管理员模式参数，也不读取未发布页面。每个请求使用独立工具执行器，无共享的回答上下文。

长期与归纳问题优先使用 Wiki；近期动态、原始证据、覆盖不足和 Wiki 不可用时使用既有 `semantic_search`、`keyword_search` 和 `get_source_detail`。回答只引用服务端返回的非空链接，并保留截止日期与争议标记。

当前 Wiki 搜索使用 MySQL 参数化全文内容/关键词/实体匹配，中文可直接检索；向量服务不是公开权限判断的依据。原有消息/总结语义 RAG 与 Wiki 并行保留，首版不强制增加 Wiki embedding 或新搜索基础设施。

## 备份、回退与诊断

备份 MySQL 中全部 `wiki_*` 表及既有原消息/图片归档，保留 `data/wiki_events/`。恢复必须是一致的整库快照，不要只复制发布指针或部分证据表。升级迁移仅新增独立表与列（2.3.2 增量添加 `wiki_chunks.applied_key`、`wiki_publications.content_hash` 与 `wiki_dirty_pages` 表），不修改旧总结、画像或 RAG 数据。

程序回退前先关闭频道 Wiki，再在 AI 用途配置中移除 `wiki`、`wiki_review` 路由，之后回退 Python/Go 与前端版本。旧版本的严格 AI 用途校验不认识新增路由。无需删除新表；如要彻底清理，先通过新版管理端逐频道清除并备份。

管理任务页显示来源处理数、缓存命中、输入/输出 Token、未核实预留、审校、发布状态与脱敏错误类型。API/日志不包含厂商密钥、内部路径或私人原文。`/wiki-preview/{数字频道ID}/{slug}` 提供同一 FastAPI 进程内的转义 HTML 预览；交互式 SPA 依赖 JavaScript，不能假定所有爬虫都会执行它。`/api/public/wiki/sitemap` 提供权限过滤后的分页路径列表。

## 验证

```powershell
# 本机一次性 MySQL，禁止指向生产库；测试会创建和删除 wiki_test_* 数据库。
$env:WIKI_TEST_PORT = '33490'
python -m pytest tests/wiki --no-cov
go -C qa-bot-go test ./...
npm --prefix web run build
```

Wiki 集成测试包括完整分页/恢复、长正文、别名、旧编辑、删除标记、并发任务、租约、审校拒绝、预算暂停、图谱、真实画像 SQL、原子发布与回滚；2.3.2 起另覆盖空增量零写入、少量新增只处理新来源、编辑/删除/图片 OCR 变化的局部重建、任务中断恢复、缓存命中跳过重写、重复发布去重与核对水位推进。跨语言用例在同一个 MySQL fixture 上调用 Go 仓库，核对发布 ID、引用策略与撤销结果。CI 使用临时 MySQL 服务执行这些测试。真实 Telegram 权限变化、实际模型知识质量和生产规模仍需部署后按频道验收。
