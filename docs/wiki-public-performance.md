# 公开 Wiki 性能与可见性验证

对应 [#161](https://github.com/Sakura520222/Sakura-Bot/issues/161)。浏览器用合成公开数据及实际生产构建，SQL 用独立 MySQL 8.4.10。生产数据和账号未参与测试。

## 浏览器

2026-11-13，Windows Chrome，1440 × 950 桌面及 Pixel 7 模拟器。移动端使用 150 ms RTT、200 KB/s 下行、90 KB/s 上行和 4 倍 CPU 降速。每组 3 次独立冷访问，表中为中位数。原版取 `4736cca`。

| 指标 | 桌面原版 | 桌面改造后 | 模拟 4G 原版 | 模拟 4G 改造后 |
| --- | ---: | ---: | ---: | ---: |
| 首页 LCP | 256 ms | 144 ms | 3,904 ms | 1,700 ms |
| 首页 CLS | 0 | 0 | 0 | 0 |
| 首页文档 TTFB | 0.7 ms | 0.8 ms | 150.2 ms | 150.1 ms |
| 首页资源请求 | 18 | 19 | 18 | 19 |
| 首页脚本 gzip 传输 | 438.2 KB | 79.6 KB | 438.2 KB | 79.6 KB |
| 打开文章至标题可见 | 275 ms | 84 ms | 960 ms | 924 ms |
| 返回首页至标题可见 | 207 ms | 13 ms | 246 ms | 83 ms |

脚本记录 Event Timing 单次交互样本。真机 INP p75、线上 Core Web Vitals 和生产 API 时延仍需部署后测量。

240 条移动端测试中，信息流发出 12 次分页请求，达到终点时有 40 张卡片挂载。测试还覆盖返回原位置、搜索高亮、频道入口、时间轴、画像图表、图谱抽屉、文章深链、按需来源、图片预览、本机收藏和深色模式。

```sh

npm --prefix web exec -- playwright-core install chromium

```

也可用 `CHROME_PATH` 指向已安装的 Chrome。设定 `WIKI_BASELINE_DIST` 为原版构建目录即可运行前后对比。设定 `WIKI_RESULTS_DIR` 可保存 JSON 和桌面、手机截图。

## 数据库

8 个频道，共 8,008 条当前快照条目，均带公开证据。每次返回 20 条。改造后的实测结果如下。

| 读取 | MySQL 中位时延 | Reader 中位时延 | Reader p95 样本 | JSON |
| --- | ---: | ---: | ---: | ---: |
| 最新 | 3.6 ms | 4.7 ms | 7.1 ms | 14.7 KB |
| 推荐 | 233.0 ms | 233.7 ms | 285.3 ms | 17.0 KB |
| 关键词搜索 | 197.4 ms | 198.1 ms | 224.3 ms | 14.7 KB |

最新流的 `EXPLAIN ANALYZE` 走 `wiki_feed_latest`，首批读取 21 个候选修订。推荐和关键词搜索先按当前发布版本连接，扫描并排序这组测试的 8,008 条候选，之后仅读取当批卡片字段。关键词搜索保留已有的中文子串、别名召回和标题加权。性能随可见快照大小、查询选择性和真实证据分布变化。

在可丢弃的 MySQL 实例上设置 `WIKI_TEST_PORT`，从仓库根目录运行 `python -m tests.wiki.benchmark_public_reads`。脚本建立并清理独立数据库，比较旧分页和游标读取，打印 SQL 计时、载荷大小和执行计划。

## 缓存边界

匿名成功响应使用私有条件缓存。每次条件请求重新核对当前发布、频道状态、主题和证据，随后才决定是否返回 304。匿名错误和管理接口使用 `no-store`。Wiki 客户端保留短期内存缓存和在途去重，页面可见时每 30 秒及切回前台检查可见性版本。检查到版本变化便清除受影响的内容。离线时内存只能展示最近一次成功读取的内容，无法感知离线期间的撤回。搜索词建议保存在当前标签会话，收藏只保存本机条目标识。
